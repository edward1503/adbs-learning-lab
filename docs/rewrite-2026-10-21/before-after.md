## Lecture 2 — SQL: understanding the result

Canonical section: `l2-1`.

**Before EN:** Suppose a shop wants eligible sales totals by city. Some conditions concern each sale, while others concern a total that does not exist until sales are grouped. SQL lets us state the desired answer, and distinguishing these intermediate meanings is the first step toward predicting it. SQL describes the desired result, such as “total sales by city”. The optimiser chooses an execution plan to compute that result. SQL normally uses bag semantics: duplicate rows remain unless duplicate elimination is requested with DISTINCT. To calculate a query result, follow the logical order FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. FROM supplies rows; WHERE filters them; GROUP BY forms groups; aggregates such as SUM combine values in each group; HAVING filters those groups. SELECT chooses output columns, DISTINCT removes duplicates, ORDER BY sorts, and LIMIT caps the number returned. This order explains the statement’s meaning; the DBMS can choose a different physical execution order that preserves the result. DDL, DML and access control DDL (data definition language) defines or changes schema objects; DML (data manipulation language) reads and changes the current data instance; DCL (data control language) manages access privileges. ## Lecture 5 — The buffer pool: pin, dirty, LRU, and CLOCK

Canonical section: `l5-1`.

**Before EN:** A query needs page P, but the buffer pool may already hold it. Checking that fact avoids unnecessary disk reads; protecting the frame while it is used avoids replacing data beneath an active operation. **After EN:** Two operations need records on the same disk page P. Reading P twice would waste work if the first copy is still in RAM. The DBMS keeps a pool of memory spaces called frames , each holding one page. This is the buffer pool. Its page table answers “which frame currently holds P?” If F0 already contains P, a request is a hit : use F0 without reading disk. If P is absent, it is a miss : choose a free frame or replace a page, then read P. A page ID identifies stored data; a frame ID identifies a reusable RAM location. The same frame can later hold another page. Suppose operation A receives P's address in F0. If B replaces F0 with Q before A finishes, A will use the wrong bytes. A pin count records active uses: pin(P) increments it; a matching unpin(P,modified) decrements it. Only pin=0 frames are candidates for replacement. Releasing P need not evict it immediately; keeping it can serve a later hit. On a hit, find the resident frame and increment its pin count. On a miss, obtain a free frame or an unpinned victim. If the victim is dirty, preserve its changed contents before overwriting it under the required persistence protocol. Read the requested page, mark the incoming copy clean, set pin=1, and return its address. After use, unpin and report whether this use modified the page. Dirty means modified in RAM since the stored copy was written. Pin answers whether someone still uses the frame; dirty answers whether RAM has unpersisted changes. These mechanisms do not replace transaction concurrency control or crash recovery. Try: every frame has pin>0. Can LRU choose the oldest anyway? No. Eligibility comes before policy ranking. The implementation must wait, report lack of a frame or use another management mechanism; it cannot overwrite an actively used frame. Is pinning a replacement for transaction concurrency control? No. It protects frame use, while concurrency control coordinates conflicting data operations. ## Lecture 16 — Access Methods

Canonical section: `l16-s1`.

**Before EN:** An access path is a way of reading data to execute an operator. For example, a selection can use a sequential scan, an index scan, or a combination of several indexes through a bitmap. Selectivity is the fraction of rows retained by a filtering condition. Original example: a table contains 10,000 rows on 100 pages, and a predicate retains 10% of the rows. A heap scan still reads all 100 pages to test the predicate, leaving 1,000 rows. If row width stays the same and the output rows are packed into pages as densely as before, the output occupies approximately 10 pages. Unclustered lookups for the 1,000 matching rows may read many scattered pages; having an index does not guarantee fewer I/Os than a scan. Key takeaway Distinguish pages read from pages remaining after filtering. Low selectivity produces a small output, but a sequential scan still reads the whole table unless some mechanism lets it skip pages. In general, a sequential scan of an input containing N pages costs N page reads. The estimate output pages ≈ selectivity × N applies only when row width and tuple packing remain unchanged. ## Lecture 21 — Recovery: why the log must come first

Canonical section: `l21-s1`.

**Before EN:** Suppose an uncommitted update reaches disk before the machine crashes. On restart, the DBMS must remove it using UNDO . Conversely, if a committed update exists only in RAM when the machine fails, the DBMS must reconstruct it using REDO . To flush a page means to write it from RAM to durable storage. A STEAL policy permits flushing pages containing uncommitted updates, so UNDO may be needed. NO-FORCE permits committing before every modified data page is flushed, so REDO may be needed. STEAL + NO-FORCE therefore requires support for both. Key takeaway STEAL requires UNDO support; NO-FORCE requires REDO support. These requirements arise because a data page may reach disk at a different time from its transaction's commit. NO-STEAL + FORCE simplifies some reasoning, but it requires retaining uncommitted pages in RAM and flushing many pages at commit. A mechanism is still needed for crashes during a multi-page flush: the two policy labels do not make a sequence of writes atomic. Which recovery direction is needed if commit is allowed while a modified page remains in RAM? Worked answer. REDO is needed to reconstruct committed work after volatile memory is lost. **After EN:** Recall the buffer pool: the DBMS edits a page in RAM, then eventually writes that page to storage. A changed page whose stored copy has not caught up is dirty . A flush writes a buffered page to durable storage. A power failure removes RAM, not the surviving disk copy in this lesson's crash model. Suppose A was 12. T1 changes it to 10 in RAM and commits, but its page has not been flushed. After a crash disk still says 12. Keeping a commit requires reconstructing the new value: REDO . Now suppose B was 7. Uncommitted T2 changes it to 3 and its page is flushed. If T2 aborts, disk must go back to 7: UNDO . These situations follow from two independent buffer-policy choices: Policy question Choice Recovery consequence May a page with an uncommitted update be flushed to free its frame? STEAL: yes; NO-STEAL: no STEAL needs UNDO support Must every changed data page be flushed before commit? FORCE: yes; NO-FORCE: no NO-FORCE needs REDO support Thus STEAL+NO-FORCE needs both directions. It makes normal operation flexible: a full buffer can evict dirty pages, and commit need not wait for scattered data-page writes. The cost is recovery machinery and a durable record of changes. NO-STEAL+FORCE reduces these two recovery needs, but uncommitted pages must fit in memory and commit writes may be expensive. Those policy names alone do not make a multi-page flush atomic: a crash halfway through still needs a correct completion/rollback mechanism. Key takeaway STEAL requires UNDO support; NO-FORCE requires REDO support. These requirements arise because a data page may reach disk at a different time from its transaction's commit. Under NO-STEAL+NO-FORCE, which recovery direction is needed after a crash? Worked answer. REDO for committed pages that never reached disk. NO-STEAL prevents unfinished updates reaching disk, so these policy choices do not require disk UNDO for them. This answer concerns the stated crash and buffer model, not every possible failure. NO-STEAL ngăn cập nhật chưa xong xuống đĩa nên các lựa chọn này không đòi UNDO trên đĩa cho chúng. Kết luận đang xét mô hình sự cố và vùng đệm đã nêu, không phải mọi kiểu hỏng.
